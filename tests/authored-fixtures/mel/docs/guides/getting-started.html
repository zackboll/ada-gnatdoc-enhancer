Getting Started

This repository is a consumer-side bridge, not a complete Skill or hardware service. The safe Ada packages use private C imports into a C++20 implementation of a C11-compatible native facade. Rust and Python clients reuse that same ABI; their supported slices differ, so do not infer RF parity from an Ada API.

Development workspace

Use Linux, Git, Python 3, GNU Make, CMake, a C11/C++20 compiler, Alire and GNAT/GPRbuild. The qualified documentation tools are Alire 2.1.1, GNAT Native 16.1.0, GPRbuild's 26.0.1 distribution (prints 26.0.0), and GNATdoc 26.0.0. The tests pin GNATformat 26.0.0. Consult the manifests before selecting tools.

repository/
  native/       ams_mel_c: CMake owns native compilation
  ada/          ams_mel: imports native/ via local development pin
    tests/      ams_mel_tests: pins ada/ and native/
  docs/toolchain/   isolated specification-only documentation project

Keep this layout intact for local development. ada/alire.toml pins ../native; ada/tests/alire.toml pins the two local crates. A resolved local build is not Alire index publication. The development manifests and release archive closure require separate packaging qualification; these instructions do not claim registry availability.

Build and test from the repository root

alr -C ada build
alr -C ada/tests run
make test-native
make test-ada
make check
make check-ada-format

Run these commands sequentially, never as parallel shared build-tree writers. The direct Make Ada targets need GPRbuild on PATH. If using Alire to supply that environment, remember that alr -C ada exec changes directory:

alr -C ada exec -- make -C .. test-ada
alr -C ada exec -- make -C .. check

Alternatively, inside ada/, use alr build and alr -C tests run. Do not run those shorter commands at repository root. Native pre-build actions run CMake; GPR imports the resulting library and does not compile the C++ implementation again. Ordinary tests use separate mock providers and require no Squall, hardware, credentials or containers.

Native loading is not provider availability

The Ada executable must resolve libams_mel_c.so.0, built under native/build/lib. Development GPR projects arrange a runtime search path; contract tests select the separate native/build-tests/lib facade and test providers. For installed applications, qualify the platform's loader search path (for example an application RUNPATH or a deliberate LD_LIBRARY_PATH) outside the checkout. Inspect readelf -d and ldd output rather than assuming build-time linking proves runtime resolution.

A runtime provider shared library supplies the published MEL factories and C++ implementations. {{package:AMS.MEL}} opens IR Sessions; {{package:AMS.MEL.RF}} and {{package:AMS.MEL.RF.C2}} open independent RF owners. Pass a provider library path and provider-defined configuration to the relevant Open operation; there is no universal configuration string. Provider dependencies and C++ ABI compatibility still matter behind the C facade. Building the bridge does not install a real provider or prove its optional capabilities.

Generate and read documentation

From repository root, with the qualified GNAT/GPRbuild on PATH and GNATDOC_PREFIX naming a qualified GNATdoc installation:

sh scripts/generate_docs_baseline.sh
python3 -m unittest discover -s scripts -p 'test_*doc*.py' -v

Open _site/index.html; the untouched complete GNATdoc reference lives under _site/api. The generator compiles specifications semantically, without a production build or runtime provider. Capability enums describe vocabulary, not a guarantee that all corresponding operations exist.
