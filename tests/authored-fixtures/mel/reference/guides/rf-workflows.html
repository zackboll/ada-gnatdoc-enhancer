RF Workflows

RF has two distinct paths: C2 allocates and controls resources, while DataMEL creates receive endpoints. They have independent owners and provider factories; neither is an IR Session. A pending future, a successful provider outcome and physical RF activity are three different facts.

Control: aperture, Job and intervals

C2_MEL
  -- Submit_Virtual_Aperture --> Virtual_Aperture_Request
  -- Wait (cached result), Claim once --> Virtual_Aperture
  -- Job_Config, Submit_Job --> Job_Request
  -- Wait (cached result), Claim once --> Job
  -- Add_Job_Intervals --> JobIntervals
  -- Finalize_Job / Cancel_Job / Wait_Job_Status

This is an illustrative operation sequence, not standalone executable Ada. AMS.MEL.RF.C2 supplies the owners, configurations and operations. Open creates an independent C2_MEL. Create_Virtual_Aperture_Config builds local copied inputs; Submit_Virtual_Aperture invokes the provider request. Wait returns cached Created/Failed data; it does not acquire ownership. Only Claim transfers the successful resource into a unique limited Virtual_Aperture.

Build a Job_Config and call Submit_Job on the aperture. Again, the Job_Request owns asynchronous completion, Wait observes the cache, and one successful Claim yields the controlled Job with copied JobDetail values. Configuration describes RX/TX groups, intervals and events, not RF execution. Add_Job_Intervals (and its compatible Add_RX_Job_Intervals name), Finalize_Job, Wait_Job_Status and Cancel_Job have separate contracts. Request Close is not Cancel_Job. Successful Add/Finalize does not prove physical transmission or reception. Preserve units and optional distinctions when building timing, pointing, modulation, user-context and waveform values.

A native worker consumes each request future once; repeatable Wait reads its cache. Timeout does not cancel. C2 child claims follow pending/unclaimed/claimed resources; Jobs retain their own aperture reference and sibling C2 claim, so public parent-first closure does not destroy resources still in use.

Data: ProductRx creation and consumption

Data_MEL
  -- Product_Rx.Submit --> Create_Request
  -- Wait, Claim once --> Endpoint
  -- provider callback --> bounded native receive queue
  -- Receive --> Event
  -- With_* scoped borrow OR Copy_* independent Ada payload

AMS.MEL.RF owns DataMEL and copied MFA information. AMS.MEL.RF.Product_Rx builds a format-specific configuration and submits the ProductRx creation request. Created means a nonnull endpoint with verified assigned format became available; it proves neither RF delivery nor hardware readiness. Claim registers the callback and acquires one Endpoint. The endpoint's ID and assigned format are cached creation values, not live status.

Current integer formats are Complex INT16 and INT8 Cartesian I/Q pairs, plus Direct INT8 and INT16 signed scalars. AMS VITA Small, Medium, Large and ExtraLarge use packet capacities of 512, 1,024, 8,192 and 32,768 bytes. The native bridge copies validated serialized packet bytes; the Ada VITA copy operations are not VITA sample decoding. Counts are pairs, scalar elements or packet objects according to the selected format, not interchangeable byte counts. PDW and Local Function receive payloads are not enabled by their enum names.

Receive returns a controlled Event holding immutable native-copied payload and Ada-owned ProductRx metadata. Metadata preserves timing, pointing and stabilization points, with absent/present-empty/present-nonempty VITA receive-event associations distinguished. With_Samples and the format-specific With operations borrow only during the synchronous processor; Copy_Samples and corresponding format-specific Copy operations allocate independent Ada values. This is not end-to-end zero-copy: the bridge already copied provider callback data.

Queue capacity and maximum event size are explicit bounds. Incoming data can be dropped and counters must be monitored. Endpoint Close stops admission and drains active callbacks under the documented contract; held Events remain independent. The exact registered callable shell and DSO are permanently retained because providers may retain references to the callback. Never manually unload it.

Descriptors, observers and conditional services

  • AMS.MEL.RF.Admin: independent administration commands; a normal Boolean rejection is not an exception.
  • AMS.MEL.RF.C2.Interval_Status: optional bounded JobInterval status observer and copied event/log values, not automatic proof of execution.
  • AMS.MEL.RF.C2.Virtual_Aperture_Notifications: observes a pending change signal, not a queue of provider status values or a recorded status-transition history. The signal contains no status snapshot, and multiple changes can coalesce. AMS.MEL.RF.C2.Virtual_Aperture_Queries performs explicit fresh status queries. Register first, query on the application thread, wait for a change signal, then query again; the subsequent query need not return a different status.
  • AMS.MEL.RF.C2.Element_Groups and AMS.MEL.RF.C2.Data_Pipes: copied descriptors, labels, endpoints and pipe information; inspecting them does not configure hardware activity.
  • AMS.MEL.RF.C2.Local_Functions: conditional Local Function catalog and status queries; these neither execute Local Functions nor perform hardware register writes. Local Function command configuration for JobIntervals belongs to AMS.MEL.RF.C2 itself, not this child query package. Both are separate from unsupported Local Function ProductRx payload delivery.
  • AMS.MEL.RF.C2.Transmit_Power: conditional power calculations; a calculated result is not a command to radiate.
